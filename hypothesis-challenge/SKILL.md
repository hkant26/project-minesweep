# 假设挑战(Hypothesis Challenge)

在方向尚未定型的最早时刻,把方案赖以成立、但没有写出来的隐含假设全部挖出来,逐个拷问。

方案写出来的部分是地面建筑,真正决定生死的是没写出来的地基——那些作者没意识到自己在假设的前提。本技能的核心是一个除法:**崩塌烈度 ÷ 检验成本**。一条致命但 3 天 0 元就能判定的假设,优先于一条同样致命但要烧 50 万才能判定的——这个排序把「先验证什么」从直觉变成算术,也把验证预算从「什么都想测」收敛到「先测最便宜的那颗地雷」。

它与姊妹技能的关系是时间轴:本技能在方向未定时挖地基;地基确认、方案定稿后,red-team 管闯关、pre-mortem 管执行。跳过挖地基直接攻击定稿方案,火力会浪费在「地基本来就不稳」的楼层上——先确认地面,再打楼。

这份分析的价值完全取决于场景的具体程度。一旦「不成立情形」写成「用户需求可能变化」,输出就一文不值。下面的每条约束都为此存在。

## 适用判断

- 适用:方向/想法/早期方案(可以只有一页纸、几段讨论记录甚至几句话),未定稿,用户想知道前提靠不靠谱、该先验证什么、值不值得往下走。
- 不适用:方案已定稿、即将闯决策关(→ red-team);定稿即将执行、想知道会怎么死(→ pre-mortem);用户还没有任何方向文本、要的是市场调研或头脑风暴(没有可挖的方案)。

## 流程

### 第 0 步:拿到方案全文

方案可能以任何形态出现,都要先拿到全文再开始:

- 文件路径 → 读文件;目录 → 读其中主要文档
- 粘贴的文本 → 直接用
- 前面对话里讨论中的想法 → 从对话完整提取,提取后向用户复述一句话摘要,防止漏抓

哪怕只有半页提纲也照常开工——模糊正是本技能的主场。完全没有方向文本时,转向调研/brainstorm,不要凭空发明假设。

### 第 1 步:锚定决策点

挖假设之前先弄清两件事,它们是「崩塌」的标定锚:

1. **下一个决策点**:这个方向如果往下走,紧挨着的决策是什么?(要不要立项?投研发?签渠道?)——「致命」的定义挂在这里:让下一个决策无法做出的假设崩塌才是致命的,崩塌烈度不能凭感觉标。
2. **已做过的验证**:哪些前提已被什么方式验证过?——已证实的不再进待验清单,避免重复烧预算。

对话里已有就直接用;缺失时从文本推断,一句话向用户复述(标注「推断」,不用等答复即可继续)。

### 第 2 步:切换到假设挖掘者

通读方案(内部思考,不输出),同时标记三样东西:作者**明说**的前提、作者没说但整个论证**踩着**的前提、作者**最自信的支柱**(= 火力目标)。

标记时顺手做两类**廉价复核**,查实的不一致直接变成一条现成的假设(「方案假设 X」被方案自己的数字或公开事实证伪,这种假设往往排位很高):

- **算术复核**:方案里的推算链条(市场规模→份额→收入,成本→回本周期)自己能对上吗?其中哪一步其实是一个未验证的假设(如利用率、转化率、留存率)?
- **外部事实核对**:引用的行业数字、日期、法规时限与公开事实一致吗?只核有把握的,不确定的交给检验动作。

### 第 3 步:挖 8-15 条隐含假设,四类扫全

- **需求假设**:用户真的有这个问题、真的痛、真的会为此改变行为/掏钱
- **供给假设**:我们能做出来、做得出成本、做得比现有替代好
- **结构假设**:市场/渠道/监管/成本结构/竞争格局会保持现状
- **时机假设**:为什么是现在;早做晚做会怎样;窗口期倒计时

每条注明「**方案明确说出**」还是「**你推断的**」(推断的给一句推断依据)。四类是覆盖性脚手架,不许跳类;某类确实无发现时明说,不为凑数硬编。

**优先挖承重的**:方案最自信的支柱下面踩着的假设,必须出现在清单里(打强不打弱)——支柱塌了才是方向级灾难,边角假设塌了只是修补。

### 第 4 步:逐条三问

1. 它不成立的**具体情形**是什么?必须是一个可被观察到的场景——谁、在什么情况下、做了什么。「用户需求可能变化」「市场可能不如预期」不是情形,是空话,作废重写。
2. 不成立时,方案是**整体崩塌**还是**局部受损**?标注:致命 / 需重构 / 需微调 / 无影响(锚定第 1 步的决策点)。
3. 用什么**最低成本**的方法能**最早**判定它成不成立?给出可执行的检验动作(方法/时长/成本)和明确判据(看到什么算不成立)。缺判据的检验等于没设计。

### 第 5 步:排序、Top 3、红线

1. 按**崩塌烈度 ÷ 检验成本**排序,标注优先级;前 3 条就是**必须先验证的**,给出建议验证顺序与时间安排(哪条先做、为什么、各花多久)。
2. 对 Top 3 各写一段**作者最可能的辩护**(为什么这个假设其实站得住)+ 判定 成立/部分成立/不成立。只有辩护不成立的假设,才真正值得先烧验证预算——辩护站得住的,排序再高也先放一放(反稻草人)。
3. **红线假设**:唯一一条「如果它错了,整个方向该换」的假设,并明确回答反身一问——Top 3 中若有任何一条被证伪,整个项目是否应该取消?是 / 否 / 取决于什么(取决于的要写清取决于哪件事)。

### 第 6 步:交稿前自检

输出草稿后、交给用户前,逐项核对:

1. **场景化扫描**:「不成立的具体情形」列里有没有挪到任何别的方案也成立的空话(判定标准:不含具体的谁/什么情况/做了什么)?有 → 作废重写。
2. **覆盖与条数**:8-15 条,四类扫全(缺类有明说)?
3. **溯源标注**:每条假设标了明示/推断?推断的有依据?
4. **检验完整性**:每条有检验动作(方法/时长/成本)+ 判据?
5. **Top 3**:有排序理由、验证顺序与时间安排、作者辩护与判定?
6. **红线与反身一问**:红线唯一?反身一问有明确回答?
7. **开场**:没有「总体来看方向不错」式缓冲句?
8. **火力分布**:最自信支柱下的假设在清单里,且排位靠前?

任何一项不过 → 修完再交。

## 输出结构

输出语言跟随用户/方案语言(中文方案出中文报告,英文方案出英文)。默认在对话中输出;用户要求时另存为 `hypothesis-report-<方案名>.md`。

**小节序号跟随报告语言**:中文报告用「一、二、…」,英文报告用「1. 2. …」——下面模板以中文形态示意,不要把中文序号或小节名照搬进非中文报告。

```markdown
# 假设挑战:〈方案/方向名〉
决策点:<一句话>(推断标注)

## 一、假设总表
| # | 假设 | 类型(需求/供给/结构/时机) | 明示/推断 | 不成立的具体情形 | 崩塌烈度(致命/需重构/需微调/无影响) | 检验方法 | 判据 | 优先级 |
(8-15 行)

## 二、必须先验证的 Top 3
每条:排序理由(烈度÷成本)/ 检验动作展开(方法/时长/成本/判据)/ 作者最可能的辩护与判定 / 验证顺序与时间安排

## 三、红线假设与反身一问
唯一「如果它错了,整个方向该换」的假设 + 反身一问的明确回答(是/否/取决于什么)

## 四、验证完成之后
一句指引:拿验证结果回来跑 red-team(闯关前)或 pre-mortem(执行前)。
```

若确实挖不出高危假设,按硬性约束 7 的兜底格式结案,不许「没有明显问题」。

## 硬性约束

这 7 条是输出质量的合同,每条针对一种具体的失效模式:

1. **反谄媚**:禁止「总体来看方向不错」「想法很有潜力,只是……」这类先扬后抑的缓冲句,直接开火。
   缓冲句是给读者的心理折扣券,让后面所有拷问显得「只是小瑕疵」。

2. **禁通用风险**:不得输出「市场变化」「执行不到位」「用户接受度待观察」这类放之四海皆准的空话。每条假设必须能指到方案的具体表述、数字、时间节点或因果链——明示假设注明「方案第 X 节说了什么」,推断假设给出推断依据。
   通用假设不可检验、不可行动;锚定原文把拷问变成可核对的陈述,也证明你真的读过方案。

3. **打强不打弱**:方案最自信的支柱(通常作者会明说「这是我们最确定的一点」)下面踩着的假设必须进清单、且排位靠前,而不是挑边角前提凑数。
   方向死于承重假设塌陷,不死于墙皮开裂;拷问支柱还有一层价值——连它都撑得住时,方向才真正值得投入。

4. **场景化**:每条「不成立的具体情形」必须是可被观察到的场景,包含谁、在什么情况下、做了什么。
   场景化把「可能不成立」变成「去这里看它成不成立」,直接接到检验动作;写不出场景,说明还没想清楚这个假设到底在赌什么。

5. **可证伪**:每条假设配最低成本最早判定的检验动作——方法/时长/成本——加明确判据。给不出判据的视为没设计完,不要写。
   检验动作把「我觉得这个前提悬」变成「3 天 0 元,看到 X 就死心」,直接变成用户的下一步。

6. **排序即结论**:优先级必须按「崩塌烈度 ÷ 检验成本」排,Top 3 唯一、红线唯一,排序逻辑显式可查。
   用户需要带走的是一个验证顺序,不是一个假设清单;「先测什么」比「有什么问题」更接近决策。

7. **最强一环兜底**:若你确实挖不出高危假设,必须写明「方案最强的支柱是 X,它之所以撑得住是因为 Y,拷问它的唯一可行路径是 Z」,不允许用「前提都比较扎实」敷衍结案。
   「都挺扎实」信息量为零;「最强支柱 + 唯一拷问路径」告诉用户真正的暴露面在哪、该盯着什么。

## 边界

- 对话内输出为主,不主动写文件。
- 本技能产出的是假设清单、验证顺序与红线,不是替用户决定做不做;验不验、走不走,决定权在用户。
- 生命周期分工:方向未定挖地基 → 本技能;定稿闯关被对手打 → red-team;定稿执行前倒推死法 → pre-mortem。用户拿**已定稿**的方案来挖假设时照做(地基复审合法),但顺手提示一句:定稿阶段的更对口工具是红队评审或事前验尸。
